# 动画格式与已确认规则

本文描述当前实现所覆盖的 TLOU Part I PC 布局，不是所有顽皮狗游戏的统一规范。历史指标见 [证据索引](evidence.md)，尚未覆盖的语义见 [开发状态](status.md)。

“解密”在本项目语境中主要指二进制结构、压缩编码与运行时语义的逆向，不应把压缩数据自动描述为密码学加密。

## 1. PAK 与资源项

PAK 由文件头、页表、指针修复表和资源项组成。资源指针不是普通绝对文件偏移：

```text
绝对文件位置 = 指针字段保存的偏移 + fixup 指定目标页的起始位置
```

存在 fixup 时，偏移 0 表示目标页起点；不存在 fixup 的裸零才可能为空。混淆二者曾导致有效 clip 被丢失。

P1 动画读取器识别的资源头为 48 字节：

| 相对资源头偏移 | 内容 |
|---|---|
| `+0x00` | 名称相对偏移 |
| `+0x08`、`+0x0C` | `0x12345` 哨兵 |
| `+0x10` | 载荷长度 |
| `+0x14` | `0x12345` 哨兵 |
| `+0x18` | 名称 StringID |
| `+0x20` | 类型 StringID |
| `+0x28`、`+0x2C` | `0x12345` 哨兵 |
| `+0x30` | 载荷起点 |

StringID 使用当前实现中的 FNV-1a 64 位计算。读取器先验证多个哨兵位置，再比较 `ANIM` 的类型哈希；一次字节模式命中本身不是资源边界的充分证据。

ANIM 载荷中，`+0x08` 指向 clip 块，`+0x10` 指向 raw channels，`+0x20` 的 u32 是目标 **SkelID**，不是旧注释中的泛称“动画组 ID”。

## 2. Clip 与分段

| Clip 相对偏移 | 当前用途 |
|---|---|
| `+0x00` | 魔数 `0x41430102` |
| `+0x0C` | u16 槽数 |
| `+0x0E` | u16 帧数 |
| `+0x1C` | float32 帧率 |
| `+0x30` | 槽表，每项 16 字节 |

每个槽包含：

```text
u32 cmdOffset, u32 constAux, u32 animOffset, u32 animAux
tagCount = (constAux >> 16) & 0xFF
bytesPerFrame = animAux & 0xFFFF
```

`tagCount` 是该段的关节数，不是可随意解释的“压缩类型标签”。每个槽有自己的命令流和逐帧数据布局，不允许只解析第 0 槽后套用到整个 clip。

## 3. 命令流与 KeyCache

命令字为 16 位：低 8 位 opcode，高 8 位操作数个数，后接相应数量的 u16 操作数；opcode 0 结束。

当前受支持布局中的关键关系：

```text
表基址 = clip 起点 + cmdOffset + (operand[2] & ~3)
KeyCache 首槽 = operand[3] // 32
表项 k 的 KeyCache 槽 = KeyCache 首槽 + k
```

op11 的位宽表按 KeyCache 槽索引，包含空洞。不能把平移数量与旋转序号简单相加当作槽号。

`decodeSegmentFrames()` 按命令顺序执行解码和散射；不支持的骨骼 opcode、缺失必要槽值或超出帧步长的位宽会拒绝对应解码路径。

当前命令遍历器仍存在需要补强的异常边界处理，不能仅因返回了一个命令列表就声称它完整到达 End。

## 4. 从散射表到模型骨骼

```text
段全局关节起点 jbase = 前面各槽 tagCount 的总和
局部关节号 = u16 表项 // 48
全局动画关节号 = jbase + 局部关节号
模型骨号 = boneMap[全局动画关节号]
```

表项余数区分 SQT 字段：

| `表项 % 48` | 含义 |
|---|---|
| `16` | 旋转字段 |
| `32` | 平移字段 |
| `0` | 缩放字段，或需结合命令判断的填充项 |

局部号超出 `tagCount` 的 SIMD 填充项不能映射成真实骨骼。对旋转表，遇到一个非旋转填充项应跳过该项，而不是丢弃整张表并压紧后续槽号。

已知样本的骨架身份：

- `ellie-skel`：`AA644C88`。
- `t1x-ellie-skel`：`1AE94937`。

这两个骨架不因都叫 Ellie 就可以互换。相同 SkelID 也是必要过滤条件，而非任意部件兼容的完整证明。

## 5. 当前编码路径

| Opcode | 作用 | 注意事项 |
|---|---|---|
| 11 | KeyCache 位宽与逐帧源位置 | 保留空洞槽；部分多次复制布局未支持 |
| 15 / 16 | 平移 / 旋转散射 | 使用 KeyCache 槽与段内输出表 |
| 21 / 23 | 未压缩常量向量 / 四元数 | 原生 float32 字序 |
| 22 | fp16 常量向量 | 区分平移与缩放 |
| 24 | Quat48 常量旋转 | 字段顺序和 swap 语义 |
| 27 | Range 向量解码 | 独立分量位宽、控制位、预测状态 |
| 28 | SmallestThree 旋转 | 描述符与缺失分量交换 |
| 29 | QuatLog 后处理 | 单个参考四元数 |
| 30 | PCA 后处理 | 左右两组参考四元数 |

### Quat48 与 SmallestThree

Quat48 的三个存储字段按 shift 33、17、2 对应 x、y、z。低两位索引表示与 w 交换的位置，不是把恢复的分量插入数组后移动其他分量。

概念上先得到三个量化分量，重建第四分量，再执行 swap。具体字段位数、尺度和符号细节以 `decodeConstQuat()` 与 `decodeQuatSmallestThree()` 为准。

构造出单位四元数不能证明字段序正确；历史绑定姿势真值正是用来区分这两种假设。

### Range 与预测

op27 不是把总位宽平均分成三份。`vec3DescriptorWidths()` 和 `decodeRangeWindow()` 解出分量位宽、控制信息、base/step 与零宽预测语义。

预测向量在每个 op27 块开始时重置。跨块继承预测会产生表面连续、但语义错误的数据。

### Log 与 PCA

```text
op29: q = q_ref ⊗ exp(v)
op30: q = q_left ⊗ exp(v) ⊗ q_right
```

四元数乘法不可交换，PCA 不能当成普通 op29。参考表包含交错存储，不能按“连续 8 字节一个四元数”的猜测排除正确位置。

### 未压缩 KeyCache

96/128 位槽直接恢复原生 float32 分量，再进入对应散射操作。压缩窗口与未压缩槽不能混用。

## 6. 输出约定

`_keyFramedBonesFromDecode()` 将源帧号转为 `frame / fps` 的时间，按 `boneMap` 映射，平移乘 `GlobalScale`，旋转采用与模型骨矩阵一致的转置约定。

无数据的骨骼保留绑定姿势，不能从已转为世界空间的骨矩阵构造缺省局部键。常量通道也需要保留；纯常量动作的持续区间不能无故变成零。

源动画 N 帧的末采样时间是 `(N - 1) / fps`。这只是解码层的约定，不能推断宿主最终写出的 FBX 一定保留了该末采样。

增量动画默认不导出；显式启用时仅尝试叠加到绑定姿势。完整 root motion、压缩定位器和非骨骼通道不在当前完整支持范围内。

## 7. 骨架与模型补充

受支持的骨架变形头魔数为 `0x41480105`；读取全量逆绑定矩阵后，检查主骨绑定变换与原 xform 一致。

现代 GEOMETRY_1 的受测布局为：

- v55：176 字节子网格描述符。
- v57：192 字节描述符，部分后续字段较旧布局多 8 字节偏移。

v57 的读取修补不意味着 PAK 回写也适配；当前回写入口显式拒绝 v57。其他版本落入旧分支不等于已验证兼容。
